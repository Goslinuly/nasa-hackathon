# Martian Map — архитектурная основа

Статус: проектное решение для обсуждения команды, 6 октября 2026 года. Основа — ТЗ 4.1, [каталог ресурсов](RESOURCES.md), правило [AGENTS.md](../AGENTS.md) и переданный команде реестр марсианских продуктов. Ограничение ТЗ 2.2 заранее подготовленными маршрутами заменено свободным выбором координат в версии 4.1; тексты ТЗ в репозитории не хранятся.

## 1. Неподвижные правила продукта

1. Любые координаты старта, цели и промежуточных точек на Марсе являются допустимым входом планировщика. Именованное место — удобная точка поиска, а не граница приложения.
2. Глобальный результат — обзорный план по доступным данным, с явными пробелами и разрешением каждого участка. Он не является подтверждённой проходимой тропой.
3. Подробный локальный путь и 3D-прогулка включаются только внутри проверенного совместного покрытия DTM, ортоизображения и пригодного графа затрат. Первоначальный район — техническая проверка этого масштаба, а не ограничение географии продукта.
4. Любое научное значение имеет источник, время, единицы, масштаб применимости и статус: измерение, производный результат, модель, справка или отсутствие данных.
5. Исходные продукты, подготовленные пакеты и рассчитанные маршруты неизменяемо привязаны к версиям. Публикация новой версии не должна менять смысл старого RoutePlan.

## 2. Форма системы

Начать с **модульного монолита FastAPI**, отдельного worker и общего PostgreSQL/PostGIS. Это сохраняет чёткие границы модулей без распределённых транзакций и нескольких API. Тяжёлые файлы и тайлы хранить в S3-совместимом объектном хранилище. Redis обслуживает очередь и временный кэш; он не является источником истины.

```text
Источники NASA / USGS / PDS / миссий
                │
       ingestion worker (Python, GDAL/Rasterio)
                │ raw → validated → derived → QA
                ├──────── PostgreSQL/PostGIS: каталог, footprints,
                │         наблюдения, публикации, маршруты
                └──────── S3: оригиналы, COG, тайлы, terrain,
                          панорамы, immutable manifests
                              │
React + TypeScript ─── FastAPI /api/v1 ─── Redis/Celery worker
   │  глобус                  │              │
   │  локальная сцена         │              └── расчёт маршрутов
   └── графики и карточки     └── поиск, покрытие, планы, наука
```

Граница API обслуживает запросы и управляет версиями. Worker импортирует данные и рассчитывает тяжёлые маршруты. Объектное хранилище/CDN выдаёт большие бинарные объекты напрямую по manifest; FastAPI не пересылает гигабайтные растры. Код импорта и маршрутизации можно запускать отдельно, но модели координат, источников и статусов остаются общим пакетом Python.

## 3. Модули backend

| Модуль | Ответственность | Не принимает на себя |
|---|---|---|
| `catalog` | источники, продукты, версии, права, проверка метаданных | расчёт маршрута |
| `coordinates` | типизированные марсианские координаты, нормализация, CRS и локальные проекции | молчаливое применение земных EPSG |
| `coverage` | footprints, маски валидных пикселей, разрешение, пригодность режима | вывод пригодности из одного bbox |
| `terrain` | подготовленные DTM/орто пакеты, manifests, графы затрат | хранение растра в бизнес-таблицах |
| `routing` | обзорный коридор, локальное уточнение, сегменты и версии алгоритма | обещание безопасности |
| `science` | слои, временные ряды, мишени, наблюдения, факты и provenance | перенос измерения соседней точки на маршрут |
| `panoramas` | точки, FOV, ориентация, hotspots и связи с мишенями | имитация непрерывной наземной съёмки |
| `plans` | пользовательские параметры, сохранение, журнал и экспорт | интерпретация научных данных |
| `publication` | импорт, QA, научное одобрение, атомарная публикация и откат | правка опубликованного пакета на месте |

Внутри каждого модуля разделить HTTP-схемы, прикладные операции, доменные типы и инфраструктуру. SQLAlchemy-модели не отдавать напрямую в API и не помещать бизнес-правила в роутеры. Зависимости направлены от HTTP/worker к прикладным операциям; доступ к PostGIS, S3 и внешним каталогам скрыт за адаптерами. Транзакция БД принадлежит одной прикладной операции. Для каждого запроса/задачи нужна отдельная сессия SQLAlchemy.

Предлагаемая структура:

```text
backend/
  pyproject.toml
  alembic/
  src/martian_map/
    api/                 # FastAPI, auth, ошибки, OpenAPI
    modules/             # catalog, coordinates, coverage, terrain,
                         # routing, science, panoramas, plans, publication
    infrastructure/      # db, object_store, queue, внешние адаптеры
    worker/              # задания импорта и расчёта
  tests/
frontend/
  src/
    app/                 # маршруты UI, providers, общий shell
    features/            # atlas, expedition, science, panorama, admin
    entities/            # типы и нормализованное состояние
    shared/api/          # клиент, сгенерированные типы OpenAPI
    shared/coordinates/  # отображение и ввод марсианских координат
infra/                   # контейнеры и локальная конфигурация
docs/
```

Не начинать с микросервисов или отдельных БД на каждую сущность. Если один модуль действительно станет узким местом, его можно выделить по этой границе позднее.

## 4. Контракт координат и пространственных данных

Канонический ввод/вывод: `body: "Mars"`, planetocentric `latitude_deg`, east `longitude_deg` в `[0, 360)`. Высота, если есть, содержит `height_m` и `vertical_datum`. Источник также сохраняет исходные latitude type, направление и диапазон долготы, CRS/WKT, погрешность и способ преобразования. Нельзя просто переименовать planetographic latitude в planetocentric или заменить CRS присвоением SRID.

Для долготы на шве 0°/360° нормализовать точки и разрезать пересекающие шов полигоны либо выполнять запрос с явным wraparound. Для планетарного каталога использовать документированную марсианскую `geometry` и GiST-индексы; расстояния и буферы в метрах вычислять только после преобразования в подходящую локальную метрическую систему. `geography` с земным эллипсоидом, EPSG:4326 и EPSG:3857 для марсианских расстояний исключены. Назначение внутреннего SRID и его регистрация в инфраструктуре должны пройти интеграционный тест до загрузки каталога.

Публичный JSON должен включать определение координат. Не маркировать марсианские координаты как обычный земной GeoJSON RFC 7946. Для фронтенда сделать один модуль преобразования между API, глобусом и локальной сценой и проверить его на опорных точках у шва и полюсов.

## 5. Хранение и минимальные связи

Первая миграция создаёт `source`, `asset`, `asset_version`, `raster_product`, `coverage_footprint`, `region`, `place`, `target`, `observation`, `layer`, `panorama`, `panorama_hotspot`, `route_plan`, `route_segment`, `publication`, `ingest_job`. Временные ряды и `route_sample` добавляются при первом подключённом ряде и профиле. Для планов сразу хранить snapshot параметров и ID публикации.

`asset_version` содержит `product_id`, URL/DOI, mission, instrument, исходный CRS, datum, разрешение, реальный footprint, `nodata`, размер, checksum, условия использования, credit, даты наблюдения/публикации/загрузки и состояние проверки. Уникальный ключ — источник + product ID + версия продукта; URL сам по себе не является стабильной идентичностью. `coverage_footprint` различает геометрию продукта и валидную область после маски NoData. Для DTM хранить качество пикселей/FOM, если продукт его предоставляет.

`route_segment` хранит геометрию, `data_level` (`local_dtm`, `orbital_overview`, `unassessed`), разрешение, coverage/mask status, source IDs, длину, неопределённость и причину деградации. `observation` ссылается на `target` или область применимости и хранит `evidence_type`, единицу, время, инструмент и качество. Геометрическая погрешность точки и footprint наблюдения — разные атрибуты.

Жизненный цикл продукта: `candidate → metadata_verified → downloaded → geometry_verified → processed → science_verified → published`. Ошибка или отсутствие поля не переводит продукт автоматически дальше. Все производные объекты указывают на исходный asset, параметры обработки, версии инструментов и checksum. Публикация переключает активный manifest одной транзакцией; старый manifest сохраняется для отката и воспроизводимости маршрутов.

## 6. Два масштаба маршрутизации

1. Проверить и нормализовать start/end/waypoints. Для каждого участка определить доступные обзорные продукты и пересечения с локальными валидными масками.
2. На всей планете рассчитать **обзорный коридор** по разреженной многоуровневой сетке MOLA и доступных орбитальных данных. Стоимость: расстояние, крупные уклоны и явно описанные ограничения. Если исходных значений недостаточно, вернуть геодезическое направление как `unassessed`, без формулировки о проходимости.
3. Внутри прошедшего QA локального пакета перевести точки в его метрическую систему и рассчитать путь по подготовленному cost-grid/графу. Исключить NoData; запретить диагональный проход между двумя запрещёнными ячейками. Проверить непрерывность на границе пакетов, прежде чем соединять локальные сегменты.
4. Разбить результат на сегменты по фактическому уровню данных. Вернуть их источники, разрешение, даты и ограничения. Профиль высот локального пути считается на числовом DTM, без интерполяции через NoData.
5. Найти научные остановки пересечением коридора и области применимости объектов; вернуть расстояние до пути и тип связи. Ближайшая мишень остаётся ближайшей мишенью, а не измерением грунта под пользователем.

Расчёт тяжёлого плана — асинхронное задание с лимитом времени/памяти, idempotency key и сохранённой версией алгоритма. Результат расчёта не зависит от того, что позже опубликована новая версия каталога. Время движения, остановок, отдельного возврата и резерва выдаётся как компоненты **симуляционной оценки**.

## 7. API и frontend

Версия `/api/v1`; вход и выход валидируются Pydantic, ошибки имеют стабильный код и человекочитаемое объяснение. Минимальные публичные контракты: `GET /coverage?lat=&lon=`, `GET /places`, `GET /layers`, `GET /panoramas`, `POST /route-plans`, `GET /route-plans/{id}`, `GET /tilesets/{id}/manifest`. Для долгого расчёта `POST` возвращает `202` и ID задания; клиент получает статусы `queued/running/succeeded/failed` через `GET`, затем результат. Публичное чтение доступно без регистрации. Административные импорт и публикация требуют ролей и аудита.

Сгенерировать TypeScript-типы и клиент из OpenAPI в CI, не поддерживать второй ручной список DTO. В состоянии UI отдельно держать введённые точки, текущий job, опубликованную версию данных, видимые сегменты и выбранный слой. Переход между глобусом, локальной сценой и панорамой сохраняет координату и ID плана; режимы имеют разные подписи. Глобусный движок выбрать после проверки Марсианского эллипсоида, тайлов, terrain и управления GPU на целевом ноутбуке; ТЗ называет CesiumJS кандидатом и Three.js резервом, но выбор пока не подтверждён. Локальную сцену и панорамы делать отдельными модулями Three.js и освобождать ресурсы неактивного renderer.

Отдельные состояния интерфейса: частичное покрытие, нет данных, неверная привязка, устаревший временной ряд, недоступный источник, ошибка расчёта. Маскот получает только опубликованные проверенные тексты и те же ссылки, что карточка науки.

## 8. Как использовать реестр продуктов

Переданный DOCX — вход в `catalog`, **не готовая загрузка данных**. Он перечисляет 37 найденных DTM по шести районам, таблицы конкретных product ID, разрешение около 1 м/пикс, площадь footprint, NoData, высоты, примерные размеры, число ортофото и URL. Все записи в нём находятся на стадии «доступ проверен»; сами растры не скачаны и совмещение не проверено. Это позволяет сразу наполнить черновой каталог и строить карту *кандидатного* покрытия, сохраняя статус проверки отдельно от доступности опубликованного локального режима.

Точки контроля при переносе:

- Гейл: текст DOCX говорит о 13 DTM, таблица содержит 12. Переданная позднее HTML-карта включает 13-й продукт `DTEEC_040770_1755_039280_1755_A01`, но у него не указаны NoData и диапазон высот. Его метаданные и общий итог 37 сверить с STAC; счётчики не использовать как критерий готовности.
- Площадь footprint не равна валидным пикселям внутри него. Для маршрутизации нужна отдельная маска NoData/FOM, а не только полигон и процент пропусков.
- Значение HiRISE DTM NoData в реестре — около `-3.402822655e38`; считывать реальный nodata из паспорта/растра и маскировать до вычисления уклонов.
- У глобальной CTX в реестре указана возможная ошибка привязки до 200 м. CTX остаётся обзорной текстурой, а не локальным основанием маршрута.
- Утверждение DOCX «все продукты CC0-1.0» проверить по **каждому** STAC item/asset и связанному ортофото до публикации. Каталог ресурсов требует продуктовых условий и кредитов; универсальное правило из одного документа принимать нельзя.
- «Больше площадь DTM» недостаточно для выбора пилота. Нужны пересечение DTM + орто + трек/панорамы + научная мишень, геометрическое качество и размер обработки. Езеро или Гейл выбираются после этой проверки. Пилот проверяет локальную детализацию, а глобальный пользовательский сценарий остаётся обязательным.

## 9. Проверки, которые защищают архитектуру

| Проверка | Ожидаемый результат |
|---|---|
| Координаты | круговой переход 359°/0°, несколько опорных точек и преобразование в локальную сцену не меняют место |
| Покрытие | точка внутри bbox, но на NoData, не открывает локальный маршрут |
| Продукт | повторный импорт той же версии идемпотентен; неверный checksum блокирует публикацию |
| Маршрут | два произвольных A/B в удалённых районах дают обзорный статус; смешанный путь показывает уровни по сегментам |
| Локальный граф | NoData и диагональ между запретными ячейками непроходимы; профиль не перескакивает через пробел |
| Наука | соседнее измерение показывает расстояние и источник, но не присваивается произвольной точке |
| Публикация | маршрут старой версии воспроизводим после публикации/отката нового manifest |
| Эксплуатация | миграция на пустой БД, резервная копия и восстановление, отказ внешнего STAC и объектного хранилища проверены |

## 10. Первый рабочий срез

1. Зафиксировать контейнеры PostgreSQL/PostGIS, FastAPI, worker, Redis, объектное хранилище и frontend; Alembic, OpenAPI и CI. Версии зависимостей выбрать и закрепить после сборки, а не по названию библиотеки в ТЗ.
2. Реализовать типизированные марсианские координаты, `source/asset_version/coverage_footprint/publication`, импорт метаданных STAC и `GET /coverage`. Показывать **кандидатное** и **опубликованное** покрытие раздельно.
3. Подключить глобальную обзорную основу MOLA и выбор произвольных A/B; вернуть обзорный или `unassessed` сегмент с источниками.
4. Проверить один локальный DTM + ортофото в их общем footprint, реальные маски и контрольные координаты. После QA подключить локальный граф и 3D-сцену для этого фрагмента.
5. Добавить одну проверенную научную мишень и панораму, затем расширять каталог, панели и десять точек по критериям ТЗ.

До 8 октября зафиксировать краткий ADR по глобусному движку и пилотному пакету; до 15 октября получить работающий импорт и совмещённый фрагмент. Сроки и полный объём выпуска остаются в ТЗ 4.1.
